# Dashboard

Source: https://docs.nestjs.com/observability/dashboard

一旦应用程序被检测并发送数据，它的项目仪表板就会自动填充，无需编写查询，也无需构建仪表板。本章介绍了每个视图显示的内容、视图如何相互关联，以及建立在遥测之上的功能（警报、SLO、问题和代理切换）如何组合在一起。有关完整参考，请参见 [NestJS Observe documentation](https://www.observe.nestjs.com/documentation)。

<figure><img src="https://www.observe.nestjs.com/docs/telemetry/dashboard.webp" alt="Project dashboard" /></figure>

> info **Hint** 下面描述的每个视图都可以在 [现场演示](https://www.observe-demo.nestjs.com/dashboard)，它在繁忙服务生成的数据集上运行仪表板：真实的请求卷、带有瀑布的跟踪、错误、作业和警报。它不需要帐户，完全在你的浏览器中运行。

#### 视图如何嵌套

几乎每个遥测视图都属于三个级别之一，您可以通过单击来在它们之间移动：

1. **分析**-列表视图。应用程序在选定窗口中报告的每个路由、作业、跨度或指标，汇总：吞吐量、延迟、故障率。这是你注意到一些事情的地方。
2. **操作** - 一条路线（`GET /orders/:id`），一个作业名称，一个跨度名称。随着时间的推移，相同的数字，加上它们背后的个人处决列表。这是确认问题形状的地方：持续或尖峰，无处不在或一个释放。
3. **执行**-单个请求、单个作业运行、单个跨度调用。它的确切持续时间、状态、用户、标签、它引发的错误、它所做的一切的瀑布，以及它写的日志。这是你诊断的地方。

聚合告诉你，事情出了问题，这有多重要；一次执行就能告诉你为什么。每个视图共享一个控制栏（时间范围和可选的应用程序过滤器），页面上的所有内容都遵循它。

#### 遥测视图

| 视图 | 它显示了什么 |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **请求** | 每一 HTTP,GraphQL,gRPC，微服务和 WebSocket 网关请求，按操作细分。请求详细信息页面将呼叫与路由自己的基线（“比 95%的呼叫慢”）进行比较，当进程陷入困境时，它会说明主机压力减慢了此操作的程度。 |
| **服务** | 每次花费的时间 NestJS**类和方法**，分为自己的时间（减去所有等待的内容）和总时间。只有工具类出现，因此短列表意味着低覆盖率，而不是低流量。 |
| **错误** | 每个未处理错误，按操作分组，失败位于页面前面：类、消息、堆栈跟踪和源代码。**分组为缺陷**开关将具有相同类别和堆栈形状的事件折叠为一个指纹组，其中包含首次/最后出现的指纹组以及引入它的版本。参见 [Error monitoring](/observability/error-monitoring)。 |
| **职位** | 后台工作-队列使用者，cron 运行-队列等待时间，尝试次数，失败原因以及持续时间和故障率。 |
| **跨度** | 对调用它们的每条路由上的跨度名称进行分析——“有多慢 `OrdersService.recalculate` 无处不在”，而不是“这一个端点有多慢”。 |
| **痕迹** | 跟踪 id 的瀑布，跨越共享它的每个服务-请参阅 [Distributed tracing](/observability/distributed-tracing). |
| **用户** | 每用户活动时 `getUserId` 配置为：每个用户的故障率、按他们执行的操作分组的调用、每个操作的重播以及它们之间的路径。**按客户分组**开关按电子邮件域列出身份。 |
| **定制** | 通过以下方式报告的计数器、仪表和汇总 [`TracerService`](/observability/manual-instrumentation#custom-metrics)，按度量名称和标签分组。 |
| **发布** | 每个 `serviceVersion` 与之前的版本相比——错误率、延迟和吞吐量并列。 |
| **日志** | 您的服务记录的所有内容（使用 `forwardLogs` 上），与他们遇到的痕迹相关。在执行页面上，每条线都放在轨迹的时钟上，紧挨着飞行中的跨度。 |
| **侧写** | CPU、内存、事件循环延迟和利用率以及每个应用程序的垃圾收集，当应用程序在多个节点上运行时，每个实例都会进行比较。单击内存或事件循环延迟图表上的尖峰，以查看当时运行的操作，并按与基线的偏差排序。 |

#### 查询、出站呼叫和捕获的请求

在跟踪瀑布、数据库查询或出站中 HTTPrequest 是创建它的方法下的一行：一个图标，操作（`SELECT orders`,`POST api.stripe.com`），以及声明或 URL 在它旁边，不悬停可见。该行的插入符打开按子句布局的完整语句，其占位符突出显示，并有一个复制按钮。值永远不会出现，因为代理会在发送任何内容之前删除它们。下面的跨度表只列出了应用程序的方法；代理的查询跨度被省略，它们的时间算作调用方法自己的时间，所以表仍然回答“我的哪个方法占用了时间”。**服务**页面遵循相同的规则：驱动程序（`pg`,`mysql2`,`mongodb`,`http`) 不列为类，查询的等待时间算作运行它的方法的自身时间。

<figure><img src="https://www.observe.nestjs.com/docs/telemetry/sql.webp" alt="A query opened in the waterfall" /></figure>

当代理保留请求自己的输入时（因为它失败了，或者运行过 [`slowerThanMs`](/observability/sdk#capturing-failed-and-slow-requests) 您配置的阈值），请求的**详细信息**卡有两个额外的折叠行，*请求头*和*请求正文*。没有捕获任何内容的请求没有这样的行。

#### 服务地图

项目的**活动→地图**页面显示其应用程序、队列和数据库如何相互通信。应用程序和队列按照调用顺序从左到右运行，每个应用程序和队列所依赖的数据库和外部服务都悬挂在它下面。一条线的粗细和沿线交通的速度显示了体积。软红色标志错误率超过 1%，全红色标志错误率超过 5%，蓝绿色意味着健康。将鼠标悬停在任何节点上，以隔离它所接触的内容，并单击它的数字：对于数据库，时间去的语句；对于一个应用程序，它调用什么和什么调用它，以及指向它的请求的链接。

<figure><img src="https://www.observe.nestjs.com/docs/telemetry/map.webp" alt="Service map" /></figure>

地图不需要配置，也不收集任何新的东西。数据库和外部主机来自代理的 [查询和出站-HTTP 跨度](/observability/sdk#database-queries-and-outbound-http)，队列来自应用程序工作的作业，应用程序之间的虚线来自共享 [痕迹 id](/observability/distributed-tracing) 的执行。每个应用程序每个驱动程序都有一个数据库节点，因此 Postgres 上的两个服务通常显示为两个数据库，因为 wire 上没有任何内容表明它们共享一个数据库。相比之下，外部主机是每个呼叫者共享的单个节点，每个应用程序最多有八个最繁忙的节点。

完全没有行的应用程序几乎总是运行一个 SDK 比 `0.3.0`，它不报告查询或出站呼叫。

> info **Hint** 应用程序之间的链接是从最近的请求中推断出来的，而不是在整个窗口中计算。将虚线读作“这个叫那个”，而不是精确的总数。

#### 将故障移交给编码代理

阅读痕迹会告诉你发生了什么。下一步总是一样的：找到代码并更改它。**复制代理提示**按钮只需单击一下即可完成移交。它将整个页面作为一个独立的降价提示复制，随时可以粘贴到 Claude 代码、光标或任何其他打开存储库的工具中。

该按钮仅出现在需要调查的地方：失败或运行速度低于 95%的同类请求或作业，或者包含错误的跟踪。该提示携带任务框架、操作上下文、带有修剪堆栈跟踪的错误和源代码行（相对于项目根重写的路径，因此 `src/orders/orders.service.ts:35` 而不是 `/var/app/current/dist/orders/orders.service.js:35`），调用如何与操作的平均值和 p95 进行比较，顶部跨度按自时间划分，多达 40 个日志行选择错误优先，以及关闭指令，要求代理从代码中解释根本原因，并提出修复方案作为测试的差异。

<figure><img src="https://www.observe.nestjs.com/docs/telemetry/copy-agent-prompt.webp" alt="Copy agent prompt" /></figure>

对于需要不断询问问题的代理（跟踪其日志，检查错误是否仍在触发），请将其连接到 [MCP 服务器](/observability/mcp-server) 反而。

#### 警报

当您的遥测超过您关心的阈值时，警报会通知您，因此您不会从客户那里发现。规则监视以下族中的一个指标：

| 家庭 | 度量 | 范围 |
| ------- | ----------------------------------------------- | --------------------------------------------------- |
| 请求 | 错误率、p95 延迟、平均延迟、吞吐量 | 一个应用程序，以及可选的一个路由+方法 |
| 工作 | 作业失败率、作业吞吐量、p95 队列等待 | 一个应用程序，以及可选的一个作业名称+队列 |
| 缺乏 | 遥测静音，作业静音 | 一个应用程序，或一个作业名称+队列 |
| 日志 | 匹配日志线 | 模式，以及可选的级别+记录器上下文 |
| 错误 | 新错误组 | 应用程序或整个项目 |
| 运行时 | 事件循环延迟，CPU 使用、内存使用 | 应用程序（每个过程采样） |
| 习惯 | 应用程序报告的任何自定义指标 | 度量名称，以及可选的一个标签 |
| SLO | SLO 燃烧速率 | 这个 SLO 本身 |

每条规则都以两种模式之一运行：**固定阈值**（“错误率高于 5%”），或**异常检测**，当指标偏离其最近的基线超过您设置的灵敏度时，异常检测将触发。异常模式通常是运行时度量的更好选择：一个固定的 CPU 对一项服务正确的阈值对另一项服务是错误的，但“与其最近的基线不同”适用于两项服务。

两个家庭直接依赖 SDK 仪器：

- **缺席检测。**遥测静音**规则监视运行时心跳 SDK 的 `runtimeMetrics` 即使应用程序处于空闲状态，采样器也会发射，一旦沉默的时间超过您设置的公差（2 分钟到 7 天），采样器就会发射。**作业静默**规则对一个命名的作业执行同样的操作，例如，一个没有运行的 cron。相同的机制为您提供了无需外部探针的轻量级正常运行时间监控和 cron 监控。一个从未报告过任何事情的范围不会开火：“尚未集成”不是“关闭”。
- **日志模式警报**计数窗口中包含子字符串的日志行（“当 `payment declined`15 分钟内出现 10 次以上”），并要求 `forwardLogs` 继续。

规则可以通过**电子邮件**、**Slack**（传入 webhook）、通用**webhook**、**应用内**通知，或者通过**创建预先填充规则严重性和范围的问题**进行通知。规则可以携带安静时间的重复静音计划，并且每个状态转换（OK→ 发射 → 解决）以每通道传递状态记录。

<figure><img src="https://www.observe.nestjs.com/docs/alerts/create-alert.webp" alt="Create alert" /></figure>

**新错误。**当出现从未见过的错误观察者时，会触发*新错误组*规则。它只计算未处理的失败：第一次出现的组回答为 5xx，或者在入口点上失败，回答为 noHTTP 状态（安 RPC 处理程序，网关消息）。代码故意抛出的错误，例如 `NotFoundException` 或者失败的验证，仍然出现在错误视图中，但不算作新的错误。每个计划，包括免费的，也会得到一个内置的**新错误电子邮件**，而无需创建规则：每个项目一封列出新错误的电子邮件，每天最多六封。每个人都可以在**设置→新建错误邮件**下关闭它。

#### 斯洛斯

SLO 将“错误率超过 5%”变成了“我们承诺 99.9%，但我们花费预算太快了”。它们是您已经收集的遥测目标，因此不需要新的仪器。安 SLO 由三个分层概念构建：

- **SLI（服务级别指示器）**：一个窗口内良好事件与总事件的比率，衡量可用性（没有未处理错误的请求）、延迟（低于您设置的阈值的请求）或作业成功。
- **目标**：SLI 加上 7、14、28 或 30 天的滚动合规窗口内的目标百分比（90-99.999%）。
- **错误预算**：错过目标的空间有多少（`1 − target`），以及**燃烧率**，即预算花费的速度。1.0 的燃烧率准时消耗；14.4 意味着 28 天的预算将在大约两天内耗尽。

燃烧率警报是一个常规警报规则，指向 SLO 而不是原始指标。典型的起点是快速燃烧规则（1 小时窗口，14.4×）、缓慢燃烧规则（6 小时，6×）和涓流规则（3 天，1×）。合规窗口不能超过您的计划保留遥测的时间。

#### 问题

问题是对遥测工作的轻量级、项目范围内的跟踪，例如值得修复的重复错误或需要调查的延迟回归。从任何执行页面手动创建它们，将错误组提升为一个错误组，或者让触发警报自动打开一个错误组。问题与请求、错误、作业或它来自的跟踪相关联，因此以后打开它的任何人都有遥测上下文，而不仅仅是对它的描述。

当您标记一个问题已解决，并且它命名了一些可测量的内容（操作、警报规则的范围）时，仪表板会根据事件发生前的基线监视该操作的遥测，并告诉您修复是否有效。它会将问题移到**验证**，然后要么自动关闭它，要么将它移回**打开**，读数会破坏它。如果您命名发行的修复程序（您的 `serviceVersion`），验证等待，直到该版本出现在遥测中。

#### 通过仪表板的工作路径

视图被设计成按顺序使用。一个典型的调查：

1. 警报触发，或者**请求**图表显示 p95 攀升。
2. 按持续时间或故障率对路由列表进行排序，以查找哪个操作移动了。
3. 打开操作。是恒定的还是尖锐的？是从部署开始的吗？检查**版本**。
4. 从分布的尾部打开单个执行，例如基线卡调用速度低于 95%的调用速度。
5. 阅读**瀑布**：哪个跨度持有自我时间？
6. 如果失败，读取**错误卡**-堆栈跟踪和抛出周围的源代码线。
7. 检查**日志**中的跟踪，悬停线条使它们与跨度对齐。
8. **复制代理提示**并将整个事情交给编码代理，或者打开一个与执行相关的**问题**，这样无论谁拿起它，都会从你停止的地方开始。

代理可以通过 [MCP 服务器](/observability/mcp-server)，每步一个工具，当您宁愿提问而不是点击浏览视图时。
